# Playwright TypeScript framework (Cucumber/BDD style) — layout & conventions

> **Windows:** lệnh trong tài liệu này viết cho Git Bash (shell Claude Code dùng trên Windows) — chạy được nguyên văn. Tự gõ trong PowerShell 5.1: thay `&&` bằng `;` hoặc chạy từng lệnh, đứng trong `automation_test/`; biến môi trường dùng `$env:TEN="giá trị"` thay cho `TEN=giá trị lệnh`. `&&` bên trong npm scripts (package.json) vẫn chạy được.

Source of truth for structure, naming and scaffolding, shared by `autotest-pw-web`, `autotest-pw-api`,
`autotest-pw-android` and `autotest-pw-jenkins`. How to write `.feature` files and step definitions:
`bdd-gherkin.md` (same folder). Examples that ran green end to end: `autotest-pw-web/examples/`,
`autotest-pw-api/examples/`, `autotest-pw-android/examples/`.

**Style: Cucumber (Gherkin).** Test cases are written as `.feature` files (Feature / Scenario /
Given-When-Then, like the course's `features/*.feature`) with **TypeScript** step definitions. Engine:
[playwright-bdd] — it turns each Scenario into a Playwright test, so fixtures, page objects, retries,
trace, HTML/JUnit/JSON reports, sharding and Jenkins all keep working. (The course runs Gherkin with
`cucumber-js` directly; that loses Playwright fixtures/reporting/parallelism — see bdd-gherkin.md §9.)

**TypeScript only.** No hand-written `.js` in `automation_test/`. `.features-gen/` holds files generated by
`bddgen` (build output, gitignored, never edited).

## 1. Layout

Same root as the RF skills (`automation_test/`) so `docs/`, `.env`, `.env.example` and
`autotest-credentials` / `autotest-project-docs` / `autotest-scenarios` / `autotest-strategy` work unchanged.
Folder names never collide with RF (`features/`, `common/`, `*.resource`, `*.robot`).

```
automation_test/
  package.json  package-lock.json  tsconfig.json  playwright.config.ts  .gitignore
  .env  .env.example                    # autotest-credentials (never read/print values)
  docs/                                 # autotest-project-docs / -scenarios / -strategy (unchanged)
  bdd/
    features/web/<feature>.feature      # Gherkin — 1 Scenario per manual TC        (≈ RF tests/<f>.robot)
    features/api/<feature>.feature
    features/android/<feature>.feature
    steps/bdd.ts                        # Given/When/Then/Before/After bound to the fixtures + @auth:<role> tag
    steps/common/*.steps.ts             # steps shared by ≥ 2 features
    steps/web/<feature>.steps.ts        # thin glue: step text → page-object call + expect
    steps/api/<feature>.steps.ts
    steps/android/<feature>.steps.ts
  config/
    env.ts                              # ENV (urls), AUTH (login contract), CREDENTIALS (getters), requireEnv

    storage.ts                          # storageState file per role (.auth/*.json) — used by @auth:<role>
    android.ts                          # (android) package, activity, serial, ANDROID_DEVICE_URL (device farm), apk
  fixtures/

    api.fixture.ts                      # api, authedApi, apiToken (worker)
    web.fixture.ts                      # poManager (POM theo khoá học)
    android.fixture.ts                  # (android) device (worker), app, functionManager
  pages/POManager.ts                    # POM theo khoá học: tạo mọi page object + getter getXxxPage()
  pages/base/BasePage.ts  pages/<feature>/<Name>Page.ts          # web page objects  (≈ RF features/<f>/*.resource)
  functions/FunctionManager.ts              # (android) cùng mẫu POManager cho function objects
  functions/base/BaseFunction.ts  functions/<feature>/<Name>Function.ts  # (android) function objects
  bdd/__screenshots__/                  # ảnh chuẩn của toHaveScreenshot() (commit vào git)
  services/base/ApiClient.ts  services/auth/AuthService.ts
  services/<feature>/<Feature>Service.ts + <feature>.endpoints.ts # API objects (≈ RF api/<f>/)
  support/data.ts  support/excel.ts     # loadData<T>() for large payloads, uniqueSuffix(); exceljs helpers
  support/dd.ts  support/dd-sync.ts     # API data-driven (Mode D): data/api/<f>.csv → `npm run dd:sync` → bdd/features/<f>.dd.feature
  bdd/steps/common/api-dd.steps.ts      # shared steps of every .dd.feature (no per-TC code)
  data/<feature>.json                   # only for payloads too big for Gherkin (optional)
  data/api/<feature>.csv                # API data-driven rows (Mode D, 1 row = 1 TC)
  tests/setup/*.setup.ts                # storageState login (project "setup") — plain Playwright, not Gherkin
  ci/summarize.ts  ci/collage.ts        # results → summary.json, failure collage
  ci/notify.ts  Jenkinsfile             # (jenkins)
  .features-gen/                        # generated by bddgen (gitignored)
  results/                              # html-report/, monocart-report/, junit.xml,
                                        # results.json, summary.json, test-results/ (gitignored)
  .auth/                                # storageState files (gitignored)
```

RF → Playwright BDD mapping:

| RF (autotest-rf-web/api/android) | Playwright BDD (autotest-pw-*) |
|---|---|
| `tests/<f>.robot` test case | `bdd/features/<f>.feature` → `Scenario: TC-001 — <Title>` |
| `[Tags]` | Gherkin tags `@TC-001 @smoke` (Feature tags inherited) |
| Test Setup / Suite Setup | `Background:` (visible precondition) or fixtures / `Before` hooks (plumbing) |
| Test Template + data | `Scenario Outline` + `Examples` |
| DataDriver CSV (autotest-rf-api Mode D, `data/api/<f>.csv`) | same CSV path + `npm run dd:sync` → `<f>.dd.feature` (api-best-practices §5a) |
| `features/<f>/<f>_variables.resource` (locators) | readonly `Locator` fields in the page object |
| `features/<f>/<f>_keywords.resource` | page-object methods, called from `bdd/steps/<f>.steps.ts` via `poManager.getXxxPage()` |
| `api/<f>/` AOM | `services/<f>/<F>Service.ts` + `<f>.endpoints.ts` |
| `common/common_keywords.resource` | `BasePage`, `BaseFunction`, `ApiClient`, `bdd/steps/common/` |
| `config/imports.resource` | `fixtures/index.ts` + `bdd/steps/bdd.ts` |
| `common_variables.resource` + `env_secrets.py` | `config/env.ts` (dotenv, same precedence, `AUTOTEST_ENV_FILE`) |
| `data/<f>.yaml` | values in Gherkin (quoted params / Examples / DataTable); `data/<f>.json` only for big payloads |
| `robot -t` | `npx bddgen && npx playwright test --grep "@TC-001\b"` |
| `output.xml` + autotest-rf-results | `results/results.json` → `npm run summary`; Playwright HTML + Monocart reports |
| `known-bug` tag | `@known-bug @fail` |
| robotidy | `npm run typecheck` + `npx bddgen` (fails on missing/ambiguous steps) |

- **Nâng/đổi version:** sửa trong `package.json` rồi `npm install`; đừng `npm install <gói>` lẻ.
- Corporate proxy: export `HTTPS_PROXY` từ `global-data.md → ## Network / Proxy`
  (credentials `PROXY_USERNAME/PROXY_PASSWORD` qua `cred_env.py run`).

## 3. Scaffold (only missing files — never overwrite)

```bash
python3 .claude/skills/autotest-pw-web/scripts/pw_scaffold.py state
python3 .claude/skills/autotest-pw-web/scripts/pw_scaffold.py core --platforms "<web,api|android|…>" --base-url "<Base URL>" --api-base-url "<API base>" --ep-login "<login endpoint|none>" --username-field "<f>" --password-field "<f>" --token-field "<f>" --token-scheme <Bearer|raw> [--web-login]
python3 .claude/skills/autotest-pw-web/scripts/pw_scaffold.py android --app-package "<pkg>" --app-activity "<activity>"
python3 .claude/skills/autotest-pw-web/scripts/pw_scaffold.py jenkins
python3 .claude/skills/autotest-credentials/scripts/cred_env.py init --scope project
```

- **`--platforms` keeps the scaffold lean, but API is a SHARED support layer, always present.** `services/` +
  `api.fixture` (+ `apiTest` in the chain) ship in every project so web/android steps can preset/verify data over
  API. `--platforms` only toggles the UI layers and whether API is also a *test target*:
  - `web` → `pages/` + `web.fixture` + `web-chromium` project (web.fixture is independent of api.fixture; both are
    merged separately in `index.ts`).
  - `android` → (via the `android` sub-command) `functions/` + android fixtures + `android` project.
  - `api` → the `api` **project** running Features tagged `@api` (API as a test target). Without it, API stays as
    support only (no `api` project).
  So: web project = `--platforms web` (web + API support); android = `--platforms android` (android + API support);
  API-only framework = `--platforms api`; combine like `web,api` or `android,api` to run API as its own target too.
  `write_index` regenerates `index.ts` from whichever fixtures exist, so order/subset are safe.
- Values come from `automation_test/docs/global-data.md` (Base URL, `## Authentication`). Missing → ask
  (Step 0c of the calling skill), never guess.
- `--web-login` (web app needs a logged-in user): enables project `setup` + `dependencies`; then create
  `tests/setup/auth.setup.ts` from `examples/tests/setup/auth.setup.ts` (adapt to the real login page) and
  one `STORAGE` entry per role in `config/storage.ts`. Scenarios opt in with the tag `@auth:<role>`.
- Windows: `python` / `py -3`; one command per line.
- `cred_env.py init` also drops `python_lib/env_secrets.py` (RF loader) — harmless, leave it.
- Output: `CREATED`, `SKIP (exists)`, `PATCHED`, `SKIP (already patched)`, `MANUAL …` (edit by hand as told).
- `state` JSON: `state` (`NEW | EXTERNAL | PARTIAL | COMPLIANT`), `features`, `specs`, `style`
  (`bdd` | `spec`), `robot_files`, `has_android`, `has_jenkinsfile`. **`style: spec`** = an existing project
  written with plain `test()` specs in `tests/<platform>/` → keep that style for it (ask before converting);
  every new project is BDD.

## 4. Conventions

**Contract.** The manual TC (`docs/features/<feature>/test-cases.md`, `### TC-NNN — <Title>`) is the
contract: same title, same steps in the same order, same expected results. Never rename, reorder, merge or
"improve" a TC. UI/API contradicts the TC → STOP and report (protocol in each SKILL.md).

**Gherkin** — full rules in `bdd-gherkin.md`. Essentials:
- One `.feature` per feature per platform; `Feature:` name = feature title; Feature tag `@<feature>`.
- One `Scenario` per TC: `Scenario: TC-003 — <Title verbatim>`; tags `@TC-003` (mandatory) + one of
  `@smoke | @regression | @negative` (+ `@known-bug @fail`, `@auth:<role>`, `@slow`).
- TC steps F[i] → `When`/`And`; expected results G[i] → `Then`/`And` right after (F/G are 1:1).
  Preconditions (D, E) → `Given`. Text in Vietnamese, as close to the TC wording as possible.
- Data visible in the step (`"…"`, `<col>` from `Examples`, DataTable). **Never credentials** — role names only.

**Run command at the top of every runnable file** — first line(s) of each `.feature`, steps file, setup
file and spec. **Luôn ghi rõ chạy TRONG `automation_test/`** (nơi có `playwright.config.ts` + `node_modules`)
— `# Chạy (trong automation_test/): npx bddgen && npx playwright test …`. Chạy ngoài thư mục đó → `bddgen`
báo "No BDD configs found" và `npx` đòi cài gói `bddgen` lạ:
```gherkin
# Chạy: npx bddgen && npx playwright test --project=web-chromium --headed --grep @cart
```
```ts
// Steps: bdd/features/cart.feature — chạy: npx bddgen && npx playwright test --project=web-chromium --headed --grep @cart
```
Add extra comment lines for special commands the file needs (e.g. `--update-snapshots` for visual TCs,
`--workers=1` for android).

**Dòng "nhiều log nhất (debug)" — ghi thêm ngay dưới dòng `# Chạy` ở mọi `.feature` (web/api/android).** Khi
cần soi lỗi, chạy biến thể verbose:
- **Log ra terminal nhiều nhất** = tiền tố `DEBUG=pw:api` (in từng action/call). Android thêm adb: `DEBUG=pw:api,pw:android`. Tối đa tuyệt đối (rất ồn): `DEBUG=pw:*`.
- **`--trace on`** = ghi **trace** đầy đủ (DOM từng bước + network + console + ảnh) — KHÔNG in ra terminal, mở bằng `npx playwright show-trace results/test-results/*/trace.zip`. Mặc định config chỉ `retain-on-failure`; `--trace on` ép ghi mọi lần. Trace áp dụng cho cả web và api (APIRequestContext).
- Mẫu: `npx bddgen && DEBUG=pw:api npx playwright test --project=<...> --trace on --grep @<feature>` (android thêm `--workers=1` + `DEBUG=pw:api,pw:android`).
- PowerShell: đặt biến riêng — `$env:DEBUG="pw:api"; npx playwright test … --trace on`.
> `DEBUG=…` chỉ gắn vào lệnh `playwright test` (không cần cho `bddgen`), và phải đứng NGAY TRƯỚC nó trong chuỗi `&&`.

**Step definitions** (`bdd/steps/<feature>.steps.ts`):
- Import `Given/When/Then/Before/After` only from `../bdd`, `expect` from `@fixtures/index`.
- Body = 1–5 lines: page-object / screen / service calls + `expect`. **No raw selectors, no `page.locator(...)`,
  no URLs** in steps — those live in page objects. **Actions:** prefer a page-object method (`login()`,
  `openSignupPopup()`); acting on a POM's exposed `readonly`/parameterised locator (`pom.getX().link.click()`,
  `pom.getX().frameLink(name).click()`) is allowed for one-offs, but if a step needs ≥2 calls on the same
  element, give it a method. **Assertions in `Then` MAY use the page object's exposed locators** via web-first
  `expect(pom.getX().someLocator)` — that is the endorsed pattern (see `examples/bdd/steps`). Values between steps → `ctx`.
- Reuse before writing: `npm run steps` (= `npx bddgen export`) lists every step; parameterise
  (`{string}`, `{int}`) instead of near-duplicates. `bddgen` fails on missing or ambiguous steps.

**Page Object Model — theo khoá học (POManager).**
- One class per page (`pages/<feature>/<Name>Page.ts`, extends `BasePage`): locators = `readonly` fields
  assigned in the constructor (lazy, no `await`), or a method returning a `Locator` for parameterised ones
  (`productCard(name)`); methods = business actions (`login`, `addToCart`) with typed params and
  `Promise<…>` returns; `expectLoaded()`-style checks allowed; TC-specific assertions stay in `Then` steps.
- `pages/POManager.ts` creates every page object once on the same `page` and exposes getters
  (`getLoginPage()`, `getCartPage()`…), exactly like the course's `pageobjects_ts/POManager.ts`.
  New page → (1) import (2) `readonly` field (3) `new` in the constructor (4) getter.
- Steps receive it from the `poManager` fixture: `async ({ poManager }) => poManager.getLoginPage().open()`.
  Never `new XxxPage(page)` in a step. Android: `functions/FunctionManager.ts` + fixture `functionManager`, same pattern.
- No hardcoded URLs — `BasePage.path` + `baseURL`.

**Imports.** Aliases `@config/* @fixtures/* @pages/* @functions/* @services/* @data/* @support/*`. Single ESM
`export` per module — never `module.exports`/`require`.

**Types.** `strict: true`; no `any` (use `unknown` + narrowing or an `interface`); `textContent()` →
`?? ''`; API payload/response = `interface` in the service file; step params typed (`email: string`).

**Credentials & env.** `config/env.ts` loads `$AUTOTEST_ENV_FILE` or `automation_test/.env` (env var > file >
empty). Secrets only via `CREDENTIALS.<web|api|app>.*` getters / `requireEnv('<KEY>')`; Gherkin says
`tài khoản "ADMIN"` and the step maps the role to `CREDENTIALS`. Keys follow autotest-credentials
(`WEB_*`, `API_*`, `APP_*`, `FARM_*`, `DB_*`, `TOTP_SECRET`, `PROXY_*`).

**Parallel vs sequential (course §19).**
| Need | How |
|---|---|
| Whole suite parallel (default) | `RUN_MODE=parallel` (default in `config/env.ts`, set at scaffold with `--run-mode`) → `fullyParallel: true`; workers = `WORKERS` env, CI 2, local auto |
| Whole suite sequential | `RUN_MODE=serial` (→ 1 worker), or per run `npx playwright test --workers=1` / `npm run test:serial` |
| Fixed number of workers | `WORKERS=4 npx playwright test …` or `--workers=4` (Jenkins param `WORKERS`) |
| Headed vs headless | **Local mặc định headed** (thấy trình duyệt chạy — tốt khi viết/chạy thử); CI headless. Đổi: `HEADED=false` (ẩn local) / `HEADED=true` (hiện CI), hoặc `--headed` trên CLI. Run-comment web ghi sẵn `--headed`. Lệnh `update-snapshots` để headless cho baseline khớp CI. |
| One feature must run in order (dependent scenarios) | tag `@mode:serial` on the `Feature:` line (failure skips the rest) — last resort, comment why |
| One feature explicitly parallel | `@mode:parallel` on the Feature (spec style: `test.describe.configure({ mode: 'parallel' })`) |
| Android | always 1 worker (one device) |

**Isolation.** Every Scenario runs alone and in parallel: no order dependency, no shared mutable state,
create own data (API in a step/fixture) and clean up in a tagged `After` hook or fixture teardown. A TC
that is itself a dependent chain = ONE Scenario.

**Size limits.** `.feature` ≤ 200 lines, steps file ≤ 200, page/screen/service ≤ 300, method ≤ 20 lines.

**Forbidden.** `page.waitForTimeout()`/sleeps · `waitForLoadState('networkidle')` as sync · `isVisible()` as an
assertion · `expect(locator)` without `await` · XPath/CSS when role/label/text/test-id works · loops over
`nth(i)` to find items (use `filter`) · `@only`/`test.only` · hardcoded URLs/credentials/absolute paths · `any`
· `module.exports` · business logic, raw selectors or `page.locator(...)` in step definitions (acting on / asserting
a POM's exposed locator is fine) · editing `.features-gen/` · `--reporter` on the
command line (replaces the configured reporters → no results.json).

## 6. `page.goto` times out everywhere (check BEFORE touching the tests)

Symptom: most or all web scenarios fail with the same error, including ones that were green before —

```
TimeoutError: page.goto: Timeout 30000ms exceeded.
  - navigating to "<BASE_URL>", waiting until "load"
```

A whole suite failing on navigation is an **environment** signal, not a locator/code one. The trap seen in
the field: the site opens fine in a normal browser and `ping`/`dig` look healthy, so the failure gets
misread as "flaky staging" and the real cause (an OS **DNS resolver** stalling exactly ~30 s on internal
hostnames) hides for hours. Run these three checks first — under a minute, and they tell you which layer:

```bash
# 1. WHERE do the seconds go? dns ≈ total  →  resolver stall (not the server, not the network)
curl -s -o /dev/null -w "dns=%{time_namelookup}s connect=%{time_connect}s total=%{time_total}s\n" "<BASE_URL>"

# 2. DNS servers vs OS resolver. dig fast + getaddrinfo slow  →  the OS resolver is the problem
dig +short <host>
python3 -c "import socket,time; t=time.time(); socket.getaddrinfo('<host>',80); print(f'{time.time()-t:.2f}s')"

# 3. Is it hostname-specific? internal host slow while google.com is instant → split-DNS/VPN scoping
python3 -c "import socket,time
for h in ['google.com','<host>']:
    t=time.time(); socket.getaddrinfo(h,80); print(h, f'{time.time()-t:.2f}s')"
```

Real measurements from a macOS + corporate-VPN machine: `dig @<ns> <host>` **0.01 s**, `getaddrinfo(<host>)`
**30.00 s**, `getaddrinfo('google.com')` **0.05 s**, raw TCP connect to the resolved IP **0.00 s**. Chromium
opened the page in **30.5 s** with the OS resolver and **0.4 s** with it bypassed — the page itself was never
slow. Because the stall is just over `navigationTimeout` (30 s), every navigation failed; the occasional
pass came from Chromium's DNS cache being warm.

| Reading | What it means | What to do |
|---|---|---|
| `dns` ≈ `total` | OS resolver stalls | fix the resolver (below), or set `DNS_HOST_MAP` to get moving now |
| `connect` large, `dns` small | network/VPN route or the host is down | VPN/route/firewall — not a test problem |
| all small, but `goto` still times out | the app really is slow to fire `load` | profile the app; only then discuss waits |

**Fix the cause** where you can: reconnect the VPN, or reload the resolver config
(macOS: `sudo killall -HUP mDNSResponder`; Linux: restart `systemd-resolved`/`dnsmasq`).

**Unblock the run meanwhile** — scaffolded projects already support it, nothing to code:

```bash
cd automation_test && DNS_HOST_MAP="<host> <ip>" npx playwright test --project=web-chromium
```

`ENV.dnsHostMap` (config/env.ts) feeds Chromium's `--host-resolver-rules` in the web project, so the OS
resolver is skipped for that host only. Empty by default, including CI. Node-side API calls still use the OS
resolver — a service that kicks off a long backend command should carry its own longer `timeout`
(api-best-practices), not a raised global one.

**Never "fix" this by raising `navigationTimeout`/`actionTimeout` or by adding retries**: it hides a machine
fault behind a slow, still-flaky suite, and the next person pays for it again. Say plainly in the report that
the run was blocked by the environment, with the numbers from the three checks above.

## 7. Mixing platforms

- API for preconditions/cleanup of UI scenarios: `authedApi` / services inside a `Given` step, cleanup in
  `After({ tags: '@<feature>' })`.
- Skip UI login: `@auth:<role>` (storageState from `tests/setup`), or `apiToken` +
  `page.addInitScript(t => localStorage.setItem('<key>', t), apiToken)` in a `Given` step before the first navigation.
- Mock/alter backend for UI edge cases: `page.route` inside a `Given` step (web-best-practices.md §8).
- Android + API: services work the same in android steps.
